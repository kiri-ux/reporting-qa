TAYLOR AGAIN - THE PAGE THAT SHIFTS UP AND WILL NOT COME BACK
=============================================================
Not a stream of bugs, a stream of good reports. This one is a real find and it
would have been very hard to describe any better than he did.

The report page is the only page in the tool laid out to NOT scroll: two panes
that scroll inside themselves so the checks and the PDF stay on screen
together. It gets that by way of overflow:hidden on the body.

overflow:hidden stops a PERSON scrolling. It does not stop a script.

The hidden file input behind the drop zone was a 1px box positioned absolutely
with nothing to be absolute inside of - and on this page, and only this page,
its containing block ends up being the whole document rather than the drop
zone. So it sat hundreds of pixels below the fold. Choose a file, the OS dialog
closes, the browser hands focus back to the input and scrolls it into view -
and there is no scrollbar to scroll back with. Stuck, exactly as he said.

The input covers the drop zone now, so there is nothing to scroll to: the thing
being focused is the thing you just clicked. And a page in that layout snaps
back to the top if anything scrolls it, so the next one of these cannot do it
either.

TAYLOR'S NOTE FIELD - ENTER WAS PRESSING THE WRONG BUTTON
=========================================================
He is exactly right, and the cause is plain HTML: Enter in a text box presses
the form's FIRST submit button. The note box sat in the same form as the two
decision icons, and the first of those is "Done, no report". So writing down
why you are chasing a file checked the row off the board.

Worse underneath: the route treated ANY unrecognized action as "done". Even a
typo would have marked a report complete. That now returns an error instead.

The note has its own Save button, first in the form so Enter reaches it and
last on the screen so it reads the way it always did. Saving a note does not
touch the verdict - the row stays on the board asking for its report - and the
note comes back in the box next time you load the page.


THE HEALTH CHECK ALARM, AND WHAT IT WAS
=======================================
The heaviest job this service runs is the order re-read: an 850 MB download and
a two-million-row parse, in the same process that serves the board. Everything
else heavy marks itself so a page load outranks it. That one never did. It ran
at full priority, and it starts one minute after a deploy - which is the minute
the person who deployed spends reloading the page to see whether it worked.

So the alarm was not random and it was not the box being small. It was the
deploy, every time, and this deploy triggered it twice over: roster.py moved,
which re-reads the orders AND re-checks every report.

Two changes:

  * It runs niced now, like everything else. A page outranks it.
  * It waits for a gap in the traffic first - no real page request for 25
    seconds - up to a fifteen minute cap, then goes anyway. Health checks do
    not count as traffic, or the gap would never come.

Why-slow says this in the half hour after a deploy, so the next alarm has an
answer on the page rather than a guess.

WHAT THIS DOES NOT FIX: the instance is one box running two workers, so a
health check that fails is the whole service, not one of a pool. If these keep
arriving on quiet days rather than deploy days, that is a size problem and
costs money.

SKYPAC 51251 - THE CANCELLED PRODUCTS
=====================================
You were right and the screen was arguing with itself. "Ordered but not on the
report: CTV, Performance Max, Video" sat directly above a panel saying of those
same three that a cancelled buy "is not part of what the campaign was asked to
deliver". Both cannot be true.

Build 162 took cancelled lines out of the pacing goal and did not take them out
of the products list, which still said a lifetime carries everything the client
ever bought, cancelled included. That is right for a buy that RAN and was then
stopped - the lifetime is what closes it out. It is wrong for a buy that was
called off, and 120731 and 120736 were called off.

So: a product is dropped from the list when EVERY line item of it inside the
campaign was cancelled. Not the row's flag - Social Mirror CTV is one row
holding a cancelled 120751 and a complete 122725 and 128151, and the flag alone
would have dropped a product that plainly ran. It reads the line items.
