SEVERAL MINUTES AFTER A DEPLOY
==============================
Two different things are in that wait, and only one of them is mine.

RENDER BUILDING THE IMAGE. Every install is a Docker build - pip, copy, push,
health check, switch. That is a couple of minutes on its own and nothing in
this code can shorten it. If the footer still shows the old build, that is
where you are.

WHAT THIS CODE DOES THE MOMENT IT COMES UP. That part was worse than it needed
to be, and Render sends traffic as soon as the container answers - so the
people who reload right after a deploy are exactly the ones who land in it.

  The sweeper started five seconds after boot. That was not "letting the first
  requests through" - it was letting the FIRST request through and then
  starting an 850 MB download and a two-million-row parse underneath the
  second one. It waits a minute now. Nothing it does is urgent; the reports it
  corrects have been on the board for hours.

  The half-deployed self-check ran before the first page could be served. It
  parses every file in the package and imports every relative target in each
  of them, in all three workers, while Render is waiting to send traffic. It
  is worth doing and it is not worth doing first - it runs in the background
  now and logs what it finds either way.

If it is still minutes after this, /why-slow will say so: "running for" tells
you whether the worker answering you had only just started, and anything over
three seconds is in the slow list underneath with what it was doing.
