THE HEALTH CHECK FAILED ON A SERVICE THAT WAS WORKING
=====================================================
Nothing was down. Render asks for /healthz, gives up after five seconds, and
calls the instance failed - and overnight it did not get an answer in time.

Two reasons, both fixed.

The order re-read is a couple of million rows of pure-Python parsing, and it
runs in a thread inside the web process. For the minutes it takes, it holds the
interpreter lock in a tight loop and nothing else in that process gets a fair
slice. It now sleeps for two thousandths of a second every four thousand rows.
A sleep - unlike a yield - actually hands the lock back, so the web side gets
to answer while the parse runs. Total cost on the real export is about a third
of a second.

And /healthz was a plain endpoint, which FastAPI hands to a thread pool - so it
queued behind whatever else was in there, on the one occasion the route
matters. It is answered directly on the event loop now, and it touches nothing:
no database, no disk. The question it answers is "is this process alive", and
anything else it asked could fail for a reason that is not that.

WHY LAST NIGHT: every build I ship changes the fingerprint of the import code,
which forces a full re-read of the order export on the next sync. You installed
several yesterday. That re-read is the heaviest thing this service does, and it
was doing it while reports were coming in.

If you see the email again: check the build in the footer against the one you
installed. If they match, the service is up and it was busy, not broken.


W&L MAZDA IS W AND L MAZDA
==========================
The report arrived filed as "W and L Mazda" and its cover page says "W&L
Mazda". Names are compared with the punctuation stripped, which turns those
into "wandlmazda" and "wlmazda" - far enough apart that the fuzzy match said
no, so a correct report was failed as a different client's. That is the loudest
finding this tool has and it was wrong.

The ampersand becomes the word "and" before the punctuation goes, so the two
spellings meet. Same for a plus sign. It still catches what it exists for - a
whole report pulled on the wrong client - and there is a test holding both
halves.

Any report already carrying that finding fixes itself in the background: this
changed the checking code, so every report re-checks.


WHEN THE SERVE FILE UPDATES
===========================
Every panel on the orders page says when it last read something and none of
them said when it looks again, so the only way to find out was to ask. The
serve panel now says:

  Checked every 30 minutes. A file dropped in that folder is picked up on the
  next check - 30 minutes at the outside - because the folder's contents are
  fingerprinted and a new or changed file changes the fingerprint. Nothing to
  press.

With a Sync now button beside it for when you do not want to wait. It reads the
serve file first, then the roster sheet, then the order export - so the serve
days land in seconds and the slow part happens behind them.
