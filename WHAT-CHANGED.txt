I have been fixing this by guessing from screenshots and telling you to press
things. That is not working, so this build does two things instead.

1. THE CHECK REFUSES TO ANSWER FROM STALE ORDER DATA.

   The export is parsed once and only the answer is kept. While the loaded rows
   were produced by an older import than the code running now, the product
   check has nothing current to compare against - so it now abstains and shows
   as skipped, with the reason. It was answering from four-builds-old data and
   producing the same wrong finding over and over, and no amount of explaining
   beats not saying it.

   So on this deploy that finding disappears until the orders have actually
   been re-read. If it comes back after a successful re-read, it is real and I
   will treat it as real.

2. EVERY REPORT NOW HAS "ORDER LINES AS STORED".

   A link under the checks on the report page. It shows the actual rows the
   report is being judged against - not the summary a finding prints:

     Product | Would be | Raw name on the order | Order | Line items |
     Live | Ran in 2026-07 | Flights | Budget

   Two columns settle it on sight:

     - WOULD BE is what today's code would map that raw product name to. Where
       it differs from Product - shown in red - the row was written by an older
       import, and that IS the answer. A row storing "Social Mirror" whose raw
       name is "Social Mirror CTV Ads" is provably from before build 42.

     - FLIGHTS shows each order's own window. "none recorded" in red means the
       row predates build 42, so the period test is falling back to the merged
       span and a gap between two flights is invisible - which is exactly the
       Blair Regional YMCA shape.

   Open that page for this report and send me a screenshot of it. Whatever is
   wrong will be visible in one of those two columns, and I will fix the actual
   thing rather than the thing I inferred.
