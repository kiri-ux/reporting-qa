THE NEW PAGE - "Why is it slow"
===============================
New icon in the left rail, under "Check a list". It shows:

  * HOW LONG THIS WORKER HAS BEEN RUNNING. This is the number I want. A cold
    start on Render is thirty to sixty seconds and it is charged to whoever
    loads the next page. If you open that page during a slow spell and it says
    the worker started forty seconds ago, that is the entire answer and none of
    my other theories matter.
  * EVERY RESTART IN THE LAST 24 HOURS, from the database, because a restart
    erases anything held in memory - including the evidence that it happened.
    Two rows at the same second is a deploy. Rows arriving on their own, four
    or five an hour, is something getting killed.
  * WHAT EACH OF THE LAST 60 REQUESTS COST THE SERVER - total seconds, how much
    of that was waiting on the database, and how many queries. If that column
    says 0.4 and your browser sat there for a minute, the time is not being
    spent in this code and I have been looking in the wrong place all week.
  * Memory held against the box's ceiling, and the load average.

It writes a plain sentence at the top when the numbers say something obvious -
"the service has restarted 6 times in the last hour, that is the reason for the
wait" - rather than leaving you to read a table of milliseconds.

Same numbers as JSON at /healthz/slow if it is easier to paste.

AND ONE REAL FAULT, FOUND ON THE WAY
====================================
Uploading an order export through the page reads it into memory three times.
Measured on your actual file: 1,046 MB of peak memory. The box has 512.

The S3 sync does not do this - it writes to a temp file and streams, 92 MB -
and that is why this has never shown up as a sync failure. It only bites the
manual upload, which is the one you used on Sunday with the 148 MB export.

The box does not survive that. The worker is killed mid-import, the platform
brings it back, and the next page load pays for a cold start. If the sweep was
running at the time it starts again from the top.

An upload over 8 MB now goes to disk first and takes the same streaming path.
Same file, same 2,427 lines, same 1,217 clients - 233 MB instead of 1,046.

I am not claiming this is the minute. It is a real bug, it is in the right
neighborhood, and it would have stayed invisible.
