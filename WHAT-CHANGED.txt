THE MEMORY LIMIT - AND IT WAS THE THIRD WORKER
==============================================
I did that. Build 169 went from two workers to three so a cheap request had
somewhere to land while the others were busy. Render then killed the instance
for exceeding memory, which is the same three workers seen from the other side:
the 2,048 MB is for the WHOLE INSTANCE, not per process. A worker was measured
holding 348 MB and an order re-read peaks a couple of hundred more on top of
one of them - three of those plus a page build each is how you reach the
ceiling.

Back to two. The health-check reason for three is much weaker now anyway:
/healthz is answered on the event loop and does nothing, so it does not queue
behind a page. And the recycler is halved - 400 requests rather than 800 - so
anything that grows gets trimmed twice as often.

Why-slow was part of the problem. It said "348 MB of 2,048 MB", which reads as
enormous headroom, on a page whose whole job is to be trusted. It says the
ceiling is shared by every worker now, with the total at that rate underneath.

IF YOU WANT THREE WORKERS, the instance has to be bigger. That is a plan change
rather than a flag, and worth it if the box keeps feeling tight - but two
should stop the restarts on its own.


YES, YOU CAN STOP A POINTLESS RE-CHECK
======================================
You are right that it was a waste, and the banner you were looking at proved
it: build 178's own note says a scheduling change no longer re-reads every PDF,
and 872 reports were being re-read because of it.

That one was unavoidable-by-design and I should have said so: 178 changed the
fingerprint FORMULA, and a hash moves when the formula changes as readily as
when a rule does. Every report was stamped with the old formula's answer, so
every report looked stale.

There is a Skip this re-check button on the banner now. It marks them current
without reading them and stops the sweep. It says plainly what it costs: if the
deploy DID change a rule, this skips corrections that were owed - and the next
deploy that touches the rules queues them again anyway.


THE DAY STRIP - WHAT THE COLORS MEAN
====================================
Three of them and no key, which is why you had to ask. There is a key now:

  filled = in the file · paler = weekend, in the file · red = nothing that day

Hover any square for how many clients delivered on it.


AND THE NEWEST DATE, PAST THE CYCLE'S MONTH
===========================================
You are right that August alone cannot answer "is this file current" - a
lifetime pulled on the 2nd of September is judged on August, so a strip showing
31 of 31 reads as up to date all through September while nothing new arrives.

Every month the file holds gets its own strip now, and above them:

  Newest day in the file: 2026-09-02. That is the whole file, not this cycle -
  if it is not close to today, the daily drop has stopped arriving whatever the
