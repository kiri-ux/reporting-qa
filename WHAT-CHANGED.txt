THE MANNING DATES CAME FROM THE ORDER HEADER, AND IT IS WRONG
================================================================
Order 55987, line item 136061. Two date pairs on that row, and they do not
agree:

  the order header    2018-03-21 -> 2018-05-18
  the line item       2026-06-29 -> 2026-07-31   (what the IO tool shows)

They do not overlap at all. The pull list was reading the header, so Manning
asked for a range back to March 2018 on the strength of a campaign that ran
for five weeks this summer.

Why the header was being read at all, rather than the line item: a lifetime
covers the whole ORDER, and line items that finished years ago are dropped at
import - so on ReThink's 4701 the header is the only surviving trace of how
far back that order goes, and using the live line item instead was the bug
fixed a few builds ago. That reasoning still holds. The header's DATES are
what turned out not to.

The same export has it the other way up too: order 36184's header starts
2024-02-07 with a line item starting 2018-01-01.

WHAT SEPARATES A GOOD HEADER FROM A BAD ONE. 55987's header ENDS before its
own line item does. A header that cannot contain its line item is not
describing it. So the header is used only when it could contain the line, and
then only if it reaches further back than the line does:

  4701    header 2018-11-01 -> 2026-12-31, line 2021-08-11 -> 2026-12-31
          header could contain it and reaches further   -> 2018-11-01
  36184   header 2024-02-07 -> 2026-12-31, line 2018-01-01 -> 2026-12-31
          header could contain it but starts later      -> 2018-01-01
  55987   header 2018-03-21 -> 2018-05-18, line 2026-06-29 -> 2026-07-31
          header ends before its own line, set aside    -> 2026-06-29

Manning's pull date becomes 2026-06-29, which is inside the bulk window - so
Manning comes off the "one pull each" list entirely.


AND THE PANEL SHOWS BOTH
===========================
The why panel prints the line item's window, and underneath it in red "header
says 2018-03-21 -> 2018-05-18" on exactly the rows where the header was set
aside. Hovering says why.

That is the thing to look at for Whitfield too. If its row is marked, the
header was the problem and this build already fixed it. If it is not marked
and says "still running", the export says that order is genuinely live and the
disagreement is between the export and the IO tool - which is worth raising
with whoever produces the file rather than working around here.
