SEO IS ITS OWN ROW NOW
======================
A client running SEO and Social Mirror was one row expecting one PDF, and those
are two files. Whichever one arrived first satisfied the row and the other was
never asked for again.

They are two rows. The products go with the right one - the SEO row says SEO
and the monthly row says Social Mirror Ads, rather than both saying both and
telling the reporter to pull each file twice. The SEO row carries an SEO tag,
its checks are skipped automatically, and both files go into the partner's
folder as before.

Three things had to move with it:

  * YOUR TRACKER ALREADY WRITES IT. "WHIT - Jefferson Hospital #54153 SEO" is
    read as an SEO row now, the same way LIFETIME is. Read as a monthly it
    would hunt for a digital row that does not exist and report every SEO
    client on your list as missing from the board.
  * EVERY REPORT ALREADY UPLOADED predates the split and is stamped "not SEO",
    including the SEO ones sitting on this cycle. Without a fallback they would
    all have come off the board as never delivered, on a deploy meant to tidy.
    A report falls back to the other row when the one it wanted is not there,
    and only then - so a client owed both keeps their two files apart.
  * THE SERVING FILE RULE got simpler and better. An SEO row never enters the
    day counting at all now, so there is no special case to maintain - and a
    mixed client's DIGITAL row is still judged by the serving file, which it
    should be, while their SEO row is not.


THE LOGAN AT DEER VALLEY - THE REASON BELONGED TO A DIFFERENT ORDER
===================================================================
It said "every line on it is an RFP" about order 51554, whose two lines are
IO Complete and ended on 15 May.

The import records why it drops rows keyed on the CLIENT, and keeps the first
reason it sees. A client with two orders has two reasons, and yesterday's fix
printed whichever came first as though it were about the order you asked about.
That is worse than no reason: it is wrong and it reads certain.

Drops are recorded per order id now, and the order's own reason wins. A row
with no order id on it still gets the client-level answer, which is the best
that can be said about it.


ON YOUR QUESTION ABOUT THE DATE RANGE - YES, NARROW IT
======================================================
The 830 MB file covers 3.6.21 to 8.26.26 at daily grain. Of the 213,394 rows in
the copy I have, the tool keeps 2,427. Everything else is read and thrown away
every morning.

NARROWING IT LOSES NOTHING, and the reason is worth knowing: every row carries
its line item's real start and end dates, so a campaign running 2021 to 2026
still reports those dates from a row dated last week. You are trimming the
daily grain, not the campaigns.

WHAT IT MUST STILL COVER. A line item needs at least one day inside the range
to appear at all, so the range has to reach back far enough to include:

  * campaigns that ended recently - lifetimes are owed the month a campaign
    finishes, and "ended 30 June, before August" is only sayable if those rows
    are in the file
  * campaigns starting soon, for next month's headroom

Six months back and two months forward covers both comfortably. For a
1 September run that is 1 March to 31 October. On what I can see that would be
something like a tenth of the current file.

AND THE TOOL NOW SHOUTS IF YOU CUT IT TOO FAR. The import replaces the order
list outright, so a narrower export takes clients off the board silently -
nothing anywhere said a number went down. A sync that comes back with more than
a quarter fewer order lines than the last one now says so on the sync record,
in those words, with both counts. Try a narrower range and check that line.
